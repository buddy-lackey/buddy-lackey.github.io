// ICMP

CHALLENGE 01 / ICMP / 5 min

A reply is not a website

A user says: “The server must work. It answers ping.”

ping 192.168.10.20
Reply from 192.168.10.20: bytes=32 time=2ms TTL=64

Browser: https://192.168.10.20 → connection failed
  1. What does the ping reply actually show?
  2. Which ICMP types were exchanged?
  3. Give two reasons why the website might still fail.
Reveal discussion

An Echo Request (type 8, code 0) received an Echo Reply (type 0, code 0). The target answered ICMP at that moment and a return path worked. This does not test the web service or TCP port 443. The service might be stopped, or a firewall might block HTTPS. A failed ping also does not prove that a host is down: ICMP may be filtered.

CHALLENGE 02 / ICMP / 5 min

Read the control messages

These are simplified IPv4 capture records. Explain each one and identify who reports the problem. 

A  192.168.10.50 → 192.168.10.1  ICMP type 8  code 0
B  192.168.10.1  → 192.168.10.50 ICMP type 0  code 0
C  192.168.20.1  → 192.168.10.50 ICMP type 11 code 0
D  192.168.30.20 → 192.168.10.50 ICMP type 3  code 3

Before D, the client sent a UDP packet to 192.168.30.20. Does D mean that ping failed?

Reveal discussion

A is an Echo Request; B is an Echo Reply. C reports TTL expiry in transit, typically from a router. D reports “Destination Unreachable: Port Unreachable”, commonly because no application listens on the destination UDP port. It reports a problem with the original UDP packet, not necessarily a ping. ICMP errors include information from the packet that triggered them.

CHALLENGE 03 / ICMP / 10 min

Watch a single ping

Use Windows and Wireshark. Identify your active adapter and default gateway using ipconfig.

  1. Start a capture on that adapter.
  2. Apply the display filter icmp.
  3. Run ping -n 1 GATEWAY_IP, replacing the placeholder with the gateway address.
  4. Find the request and reply. Record source, destination, type, code, identifier and sequence number.
  5. How can you tell that the reply belongs to the request?

Compare results with a neighbour. If the gateway does not answer, use a lab host selected by the teacher.

Reveal discussion

The request normally has type 8/code 0; the reply has type 0/code 0. Source and destination swap. Identifier and sequence number link the pair; the payload is echoed. A display filter hides other packets without stopping their capture. ICMP runs directly inside IPv4 and has no TCP/UDP port numbers.

CHALLENGE 04 / ICMP / 7 min

Follow the TTL

tracert -d 8.8.8.8

1    1 ms    1 ms    1 ms   192.168.10.1
2    *       *       *      Request timed out.
3    9 ms    8 ms    9 ms   198.51.100.1
...  destination eventually responds
  1. Why does the first router respond to a probe sent with TTL=1?
  2. Does row 2 prove that router 2 cannot forward traffic?
  3. Which filter shows TTL-expiry messages in Wireshark?

Optional: run the command yourself and compare the output with the capture.

Reveal discussion

The router reduces TTL to zero, discards that probe and normally sends ICMP Time Exceeded (type 11/code 0). Later probes use higher TTL values. Row 2 only shows that no response arrived in time; replies may be filtered or rate limited. Later replies show that some probes got farther. Use icmp.type == 11. Windows tracert uses ICMP Echo probes; Linux traceroute commonly defaults to UDP.

// ARP

CHALLENGE 05 / ARP / 5 min

Whose MAC do we need?

PC-A:     192.168.10.50/24
Gateway:  192.168.10.1
PC-B:     192.168.10.60/24
Server:   192.168.20.20/24
ARP cache: empty
  1. PC-A sends to PC-B. Which IP address does it ask about using ARP?
  2. PC-A sends to the server. Which IP address does it ask about now?
  3. For the server packet, state the destination IP and the destination Ethernet MAC on PC-A’s first link.
Reveal discussion

For PC-B, PC-A resolves 192.168.10.60. For the remote server, it resolves its next hop: 192.168.10.1. The server remains the destination IP; the gateway’s MAC is the destination Ethernet address on the first link. ARP resolves a local next hop, not a remote host across routers. Assume ordinary connected routes and a default route via this gateway.

CHALLENGE 06 / ARP / 7 min

Two headers, two purposes

Decode this ordinary ARP request:

Ethernet source:       02:00:00:00:00:50
Ethernet destination:  ff:ff:ff:ff:ff:ff
EtherType:             0x0806

ARP opcode:            1
Sender MAC:            02:00:00:00:00:50
Sender IP:             192.168.10.50
Target MAC:            00:00:00:00:00:00
Target IP:             192.168.10.1
  1. Why are the Ethernet destination and ARP target MAC different?
  2. What would opcode 2 mean?
  3. Is an IPv4 header needed between Ethernet and ARP?
Reveal discussion

The Ethernet broadcast reaches devices in the VLAN. Inside ARP, the target MAC is unknown and is represented here by zeros. Opcode 2 means ARP Reply, normally sent as unicast to the requester in this exchange. ARP is carried directly in Ethernet with EtherType 0x0806, without an IPv4 header.

CHALLENGE 07 / ARP / 10 min

Catch ARP before ICMP

  1. In Wireshark, capture on your active adapter and use arp || icmp.
  2. Run arp -a and check whether your gateway already appears.
  3. Ping the gateway once: ping -n 1 GATEWAY_IP.
  4. Find any ARP request/reply followed by ICMP. Explain the order.

No ARP exchange? The mapping may already be cached. In an isolated lab, an elevated Windows terminal can remove only that entry with arp -d GATEWAY_IP. Start capturing before pinging again. Avoid clearing the entire table.

Alternative: use two PCs and one switch in Packet Tracer, in the same /24. In Simulation mode, filter for ARP and ICMP and send one Simple PDU between the PCs.

Reveal discussion

Before sending the unicast Ethernet frame, the sender needs the next-hop MAC. If it has no usable mapping, ARP normally runs first. A cached mapping removes that need. Background traffic may also resolve the address before your ping. In Packet Tracer, the first PDU can fail or take extra steps while ARP completes; inspect the event list and repeat if needed.

CHALLENGE 08 / ARP / 5 min

The table changed

Previously verified gateway MAC:
192.168.10.1 → 02:00:00:00:00:01

Current PC ARP cache:
192.168.10.1 → 02:00:00:00:00:99
192.168.10.60 → 02:00:00:00:00:60
  1. What could happen to outgoing frames?
  2. Is this sufficient evidence of an attack?
  3. How does this table differ from a switch MAC table?
Reveal discussion

Frames for the gateway go to the newly mapped MAC. A false mapping could enable interception or cause an outage. A legitimate gateway replacement or failover could also change it, so verify against trusted configuration and captures. An ARP cache maps IPv4 addresses to MAC addresses; a switch MAC table maps MAC addresses to switch ports within VLANs. A managed L2 switch may use ARP for its own management IP traffic.

// DHCP

CHALLENGE 09 / DHCP / 5 min

Rebuild DORA

A newly connected client has no usable lease. Put these messages in order and describe who sends each: 

A  DHCPACK
B  DHCPDISCOVER
C  DHCPREQUEST
D  DHCPOFFER
  1. Which UDP ports do the client and server use?
  2. How can the client send its first message before it has an assigned IPv4 address?
  3. Name three settings besides the IP address that DHCP can provide.
Reveal discussion

B → D → C → A: Discover, Offer, Request, Acknowledge. The client sends Discover and Request; the server sends Offer and ACK. DHCPv4 uses UDP 68 on the client and UDP 67 on the server. Initial Discover can use source 0.0.0.0 and destination 255.255.255.255, carried in an Ethernet broadcast. Settings include subnet mask, default gateway and DNS servers. Offer and ACK delivery can vary; do not assume every DHCP message is always broadcast.

CHALLENGE 10 / DHCP / 7 min

An address is not enough

Compare these simplified Windows outputs:

CLIENT A                     CLIENT B
DHCP enabled: Yes             DHCP enabled: Yes
IPv4: 169.254.44.12           IPv4: 192.168.10.75
Mask: 255.255.0.0             Mask: 255.255.255.0
Gateway: (none)               Gateway: 192.168.10.1
DHCP server: (none)           DHCP server: 192.168.10.5
DNS: (none)                   DNS: 192.168.10.53
  1. Which client appears to have a DHCP lease?
  2. Suggest two checks for client A.
  3. Client B reaches a server by IP but not by name. What should you investigate next?

Inspect your own configuration with ipconfig /all. Find the lease times, DHCP server and DNS servers. Do not publish your full output.

Reveal discussion

B appears to have received a lease. A has a link-local/APIPA address, suggesting that it did not obtain a usable DHCP lease. Check link/Wi-Fi and VLAN membership, then DHCP availability, pool capacity or relay configuration. The address alone does not identify the root cause. For B, investigate DNS configuration and name resolution; an IP test does not test DNS.

CHALLENGE 11 / DHCP / 7 min

The lease clock

A client receives an 8-hour lease at 08:00. Assume the usual T1=50% and T2=87.5%, no successful renewal and no DHCPNAK.

  1. When does it first try to renew, and to which server?
  2. When does it begin rebinding using broadcast?
  3. When must it stop using the address?
  4. Must the client immediately stop working if the DHCP server goes offline at 09:00?

Bonus: does ipconfig /renew necessarily produce all four DORA messages?

Reveal discussion

T1 is 12:00: the client normally unicasts DHCPREQUEST to its original server. T2 is 15:00: it broadcasts DHCPREQUEST to seek a response from any suitable server. The lease expires at 16:00, so it must stop using that address if no renewal succeeded. An existing valid lease remains usable during a server outage. DHCP can specify different T1/T2 values. A manual renew may renew an existing lease using Request/ACK without a complete Discover/Offer exchange.

// BOSS

CHALLENGE 12 / BOSS / 10 min

A new VLAN, a silent client

VLAN 10 clients: 192.168.10.0/24 — DHCP works
VLAN 20 clients: 192.168.20.0/24 — DHCP fails
DHCP server:    192.168.10.5
VLAN 20 gateway:192.168.20.1

Capture inside VLAN 20:
0.0.0.0:68 → 255.255.255.255:67  DHCPDISCOVER
(repeated; no offer seen)
  1. Why does an ordinary router not simply forward this broadcast?
  2. What function could relay the request to the server?
  3. What scope and gateway setting does the server need for VLAN 20?
  4. Could a pure L2 switch forwarding broadcasts inside VLAN 20 solve the cross-subnet problem?
  5. After DHCP works, describe the roles of DHCP, ARP and ICMP when the client pings 192.168.10.5.
Reveal discussion

Routers do not normally forward local IPv4 limited broadcasts. A DHCP relay on the VLAN 20 gateway can relay requests to 192.168.10.5. The server needs a suitable 192.168.20.0/24 scope with default gateway 192.168.20.1; routing and relevant firewall rules must permit the exchange. The relay provides subnet information so the server can choose the scope. A plain L2 switch cannot solve this by ordinary switching; a managed switch needs an explicit relay feature to act as a relay.

DHCP supplies the client configuration. For the remote server, ARP resolves the local gateway MAC. ICMP supplies Echo Request/Reply. Inter-VLAN routing and policy must permit the ping. The missing Offer is a clue, not proof that relay is the only possible fault.
