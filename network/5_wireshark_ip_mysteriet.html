LECTURE 05 // IPv4

Wireshark: fallet med den försvunna MAC-adressen

● NETWORK ONLINE_

Cirka 35–50 minuter · Arbeta ensam eller i par

Tre olika IP-mottagare dyker upp i spårningen. Men flera paket får samma destination-MAC. Har de skickats till fel dator?

Du undersöker din egen IPv4-trafik med Wireshark och Windows-kommandon. Använd skolans vanliga nätverksanslutning. Om skolans miljö tillåter det, koppla från eventuell VPN för ett tydligare resultat.

// STEP 01 — Samla ledtrådar

ipconfig /all

Anteckna IPv4-adress, nätmask, fysisk adress och default gateway för den aktiva anslutningen. Beräkna din nätadress.

Om flera adaptrar visas, välj den som faktiskt används.

Skriv en hypotes: Vilken destination-MAC kommer en ping till 1.1.1.1 att ha?

// STEP 02 — Fånga tre pingtester

  1. Starta inspelning på den aktiva Ethernet- eller Wi-Fi-adaptern. Använd inget capture filter.
  2. Pinga din gateway: ersätt GATEWAY_IP med adressen från ipconfig.
  3. Pinga två externa adresser och stoppa sedan inspelningen.
ping -4 -n 1 GATEWAY_IP
ping -4 -n 1 1.1.1.1
ping -4 -n 1 8.8.8.8

Använd följande display filter:

icmp.type == 8

Välj de utgående Echo Request-paketen från din egen dator. Expandera Ethernet II och Internet Protocol Version 4.

Fyll i tabellen i dina anteckningar. Du kan undersöka de utgående paketen även om ping inte får svar.

Vanlig Wi-Fi-inspelning i Windows visar ofta Ethernet II. Om fångsten visar råa 802.11-ramar finns fler MAC-fält. Be läraren hjälpa till med tolkningen eller använd Ethernet för denna del.

Ledtråd

Destination-IP anger den slutliga IP-mottagaren. Destination-MAC anger mottagaren på den lokala länken.

// CHALLENGE — Lös fallet

  1. Hur många olika destination-IP ser du? Hur många olika destination-MAC?
  2. Varför behöver datorn normalt inte känna till MAC-adressen för 8.8.8.8?
  3. Kontrollera gatewayens MAC med kommandot nedan. Stämmer den med fångsten?
  4. Visar fångsten den publika IP-adressen för din internetanslutning? Förklara var en vanlig NAT-router ändrar käll-IP.
arp -a

Filtrera även på arp. Om inga ARP-paket syns kan gatewayens MAC redan vara cachad. Det är ett fynd, inte ett fel.

Valfritt: fånga ett nytt ARP-utbyte

På en lärargodkänd labbdator kan du i en administratörsterminal radera endast gatewayposten:

arp -d GATEWAY_IP

Ersätt GATEWAY_IP med den riktiga adressen. Starta inspelningen före nästa ping. Datorn kan då behöva fråga efter gatewayens MAC igen.

Du behöver inte radera posten för att slutföra labben.

// BONUS — Ett paket som aldrig kommer fram

Starta en ny inspelning. Skicka ett enda Echo Request med TTL 1:

ping -4 -n 1 -i 1 1.1.1.1

Stoppa inspelningen och filtrera på icmp.

  1. Vilken TTL har den utgående IPv4-headern?
  2. Får du ICMP Time Exceeded, typ 11? Vem skickar det?
  3. Expandera svaret. Hittar du en inbäddad kopia av det ursprungliga paketets IP-header?
  4. Varför kan samma paketdetaljer visa två IP-headers med olika adresser?
  5. Vilket verktyg upprepar principen med successivt högre TTL?

Om inget svar kommer: dokumentera det. Routrar och brandväggar kan begränsa ICMP-svar. Uteblivet svar bevisar inte att paketet nådde slutmålet.

Reveal discussion

I en vanlig miljö med en default gateway går alla tre tester till gatewayens MAC på den lokala länken. IP-mottagarna skiljer sig.

Datorn ARP:ar efter gatewayen, inte efter internetservern. Specialroutes eller VPN kan ge andra resultat.

En fångst på datorns LAN-adapter visar normalt dess lokala käll-IP. NAT sker senare vid routern.

Echo Request är ICMP, även när mottagaren råkar vara en DNS-server.

TTL 1 gör att den första vidarebefordrande routern normalt kastar paketet och kan skicka ICMP typ 11, kod 0.

Svaret innehåller en yttre IP-header för felmeddelandet tillbaka till dig. Inuti ICMP-meddelandet finns information från paketet som orsakade felet, inklusive dess IP-header.

Traceroute/tracert använder principen. Svarets egen TTL är inte samma sak som TTL i det citerade paketet.
