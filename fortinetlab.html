06 // TO THE FIREWALL VS THROUGH THE FIREWALL

CHECKPOINT 5p

Vad har vi egentligen bevisat?

PC-A kan kommunicera med 192.168.1.99. PC-B kan kommunicera med 192.168.2.1.

Kan PC-A därför automatiskt kommunicera med PC-B?

Nej.

Hittills har trafiken sett ut så här:

PC-A → FORTIGATE PC-B → FORTIGATE

FortiGate har varit destinationen.

När PC-A ska nå PC-B ser trafikflödet istället ut så här:

PC-A 192.168.1.10 | v FORTIGATE | v PC-B 192.168.2.10

Nu måste FortiGate vidarebefordra trafik mellan två olika nät. Routing och firewall policy blir därför relevanta.

13 // STATEFUL VS STATELESS

CHALLENGE 03 12p

Stateful eller stateless?

En stateless packet filter bedömer paket utan samma typ av sessionsinformation som en stateful brandvägg.

FortiGate är stateful och håller information om trafikflöden.

ICMP är bra för att demonstrera IP, routing och policyfiltrering. TCP är bättre när vi vill studera portar, TCP-handshake, etablerade sessioner och returtrafik.

Därför använder nästa del TCP/8000.

14 // ADVANCED BONUS — TCP SERVER

ADVANCED BONUS 20p

Publicera en resurs på PC-B

PC-B ska publicera en enkel HTTP-resurs på TCP-port 8000.

Vi använder PowerShell och .NET. Ingen Python, netcat eller IIS behövs.

Steg 1 — öppna TCP/8000 i Windows Defender Firewall

Kör PowerShell som administratör på PC-B.
New-NetFirewallRule -DisplayName "FortiLab TCP 8000" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow

Verifiera:

Get-NetFirewallRule -DisplayName "FortiLab TCP 8000"
WINDOWS DEFENDER FIREWALL STATUS: ON TCP/8000 INBOUND STATUS: ALLOW
ADVANCED BONUS 20p

Steg 2 — starta TCP-servern

Öppna ett nytt PowerShell-fönster på PC-B och kör:

$port = 8000 $listener = New-Object System.Net.Sockets.TcpListener( [System.Net.IPAddress]::Any, $port ) $listener.Start() Write-Host "FortiLab server lyssnar på TCP/$port" Write-Host "Avsluta med CTRL+C" try { while ($true) { $client = $listener.AcceptTcpClient() $remote = $client.Client.RemoteEndPoint Write-Host "" Write-Host "Anslutning från $remote" $stream = $client.GetStream() $reader = New-Object System.IO.StreamReader($stream) $request = $reader.ReadLine() Write-Host "Request: $request" $body = @" FORTILAB SERVER PC-B svarar pa TCP port 8000. Remote client: $remote Request: $request "@ $bodyBytes = [System.Text.Encoding]::UTF8.GetBytes($body) $header = "HTTP/1.1 200 OK`r`n" + "Content-Type: text/plain; charset=utf-8`r`n" + "Content-Length: $($bodyBytes.Length)`r`n" + "Connection: close`r`n" + "`r`n" $headerBytes = [System.Text.Encoding]::ASCII.GetBytes($header) $stream.Write( $headerBytes, 0, $headerBytes.Length ) $stream.Write( $bodyBytes, 0, $bodyBytes.Length ) $stream.Close() $client.Close() } } finally { $listener.Stop() }

När servern startat ska PC-B visa:

FortiLab server lyssnar på TCP/8000 Avsluta med CTRL+C

18 // WHY DOES RETURN TRAFFIC WORK?

STATEFUL CHALLENGE 20p

En policy — men trafik åt båda håll?

Ni skapade:

192.168.1.0/24 | | TCP/8000 v 192.168.2.0/24 ACCEPT

Ni skapade inte motsvarande policy från Network B till Network A.

Ändå kan PC-B skicka svar tillbaka till PC-A.

Varför?

FortiGate är stateful.

När PC-A initierar en tillåten TCP-anslutning håller brandväggen information om sessionen.

192.168.1.10:53172 ↓ 192.168.2.10:8000 SESSION: ESTABLISHED

Svarstrafiken kan därför identifieras som trafik som hör till den redan etablerade sessionen.

Det betyder inte att PC-B automatiskt får initiera helt nya anslutningar mot PC-A.
