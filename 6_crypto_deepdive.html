WHAT IS ACTUALLY SIGNED?

Du vet redan att publika och privata nycklar används för kryptering och digitala signaturer. Nu kommer de jobbiga frågorna. Var ligger hashvärdet? Vad är egentligen en digital signatur? Vad händer om vi både signerar och krypterar? Och varför litar datorn på ett certifikat?

Målet här är inte att memorera fler ord. Målet är att kunna följa datan genom hela processen.
00 // HASH ÄR EN MELLANPRODUKT

En vanlig missuppfattning är att ett digitalt certifikat innehåller både ett hashvärde och en signerad kopia av samma hash.

Förenklat ser processen istället ut så här:

CERTIFICATE DATA │ │ ▼ HASH() │ ▼ DIGEST │ │ + CA PRIVATE KEY ▼ SIGNATURE ALGORITHM │ ▼ DIGITAL SIGNATURE

Hashvärdet behövs för att skapa signaturen, men behöver normalt inte lagras som ett eget fält. Klienten kan beräkna hashvärdet igen.

01 // SIGN THEN ENCRYPT

Antag att Alice vill skicka en fil till Bob. Hon vill ha både:

Riktighet + autentisering genom digital signatur och konfidentialitet genom kryptering.

ALICE
FILE │ ├── HASH │ │ │ ▼ │ SIGN │ │ │ ▼ │ SIGNATURE │ ▼ FILE + SIGNATURE │ ▼ ENCRYPT FOR BOB │ ▼ CIPHERTEXT
BOB
CIPHERTEXT │ ▼ DECRYPT │ ▼ FILE + SIGNATURE │ ├── HASH FILE │ └── VERIFY SIGNATURE │ ▼ VALID?
Det finns flera riktiga kryptografiska protokoll och format. Bygg därför inte egna kryptografiska protokoll utifrån den här förenklade modellen. Här använder vi modellen för att förstå principerna.
[ BASIC ] // FOLLOW THE DATA
QUESTION 01
Alice har filen: rapport.pdf Hon beräknar SHA-256 över filen. Vad får hon?
A) En krypterad PDF
B) Ett hashvärde med fast längd
C) En digital signatur
B. Hashfunktionen producerar ett hashvärde. Ingen signering har ännu skett.
QUESTION 02
Alice ändrar ett enda tecken i dokumentet. Vad händer med SHA-256-värdet?
Tänk på avalanche-effekten.
Hashvärdet blir i praktiken helt annorlunda. Det är detta som gör att förändringar i data lätt kan upptäckas.
QUESTION 03
Har Alice bevisat att det är hon som skapade dokumentet bara genom att publicera SHA-256-värdet?
Nej. Vem som helst kan beräkna ett hashvärde. Hash ger inte i sig autentisering av avsändaren. Det är därför digital signatur tillför något ytterligare.
[ INTERMEDIATE ] // DIGITAL SIGNATURE
QUESTION 04
Vad används för att skapa Alices digitala signatur?
A) Alices publika nyckel
B) Bobs publika nyckel
C) Alices privata nyckel
D) Bobs privata nyckel
C – Alices privata nyckel. Bob verifierar sedan signaturen med Alices publika nyckel.
QUESTION 05
Ligger det ursprungliga SHA-256-värdet nödvändigtvis som ett separat fält bredvid signaturen?
Nej. Hashvärdet är normalt en mellanprodukt. Verifieraren kan själv beräkna ett nytt hashvärde över datan. Signaturen lagras däremot.
QUESTION 06
Mallory ändrar fältet Subject i ett CA-signerat certifikat efter att det utfärdats. Kan Mallory bara låta den gamla signaturen ligga kvar?
Signaturen kan ligga kvar rent som bytes, men den kommer inte längre att verifiera. När klienten beräknar hash över det modifierade innehållet kommer resultatet inte längre passa den digitala signaturen.
[ CHALLENGE ] // SIGN + ENCRYPT
QUESTION 07
Alice ska skicka secret.txt till Bob. Hon gör:
1. signera filen 2. kombinera FILE + SIGNATURE 3. kryptera paketet för Bob

Vilken information kan Eve se utan Bobs privata nyckel?

I den förenklade modellen ligger både filen och signaturen inne i det krypterade innehållet. Eve kan därför inte läsa filen eller den inneslutna signaturen utan att kunna dekryptera paketet.
QUESTION 08
Bob dekrypterar paketet. Han får:
FILE + ALICE'S SIGNATURE

Vilken nyckel behöver Bob nu för att verifiera signaturen?

Alices publika nyckel. Det är alltså en annan nyckel än den som användes när Bob dekrypterade med sin privata nyckel.
QUESTION 09
Vilka två helt olika saker bevisar de två lagren?
Operation Nyckel Vad vill vi uppnå?
Signering ? ?
Kryptering till Bob ? ?
Signering:
Alices privata nyckel → riktighet och autentisering.

Kryptering:
Bobs publika nyckel → konfidentialitet.
QUESTION 10
Varför bör vi inte säga:
"Alice krypterar hashen med sin privata nyckel"

som en universell teknisk definition av digital signatur?

Fundera på om RSA och ECDSA fungerar exakt likadant.
Formuleringen fungerar ibland som pedagogisk förenkling, framför allt när man introducerar RSA. Men olika signeringsalgoritmer använder olika matematik. En bättre generell formulering är:

Signeringsalgoritmen använder hashvärdet och den privata nyckeln för att skapa en digital signatur.
[ ADVANCED ] // WHO DO YOU TRUST?
QUESTION 11
Du verifierar signaturen på:
www.example.com │ ▼ Intermediate CA │ ▼ Root CA

Vem signerar Root CA-certifikatet?

Ett root-certifikat är normalt självsignerat. Men självsigneringen är inte i sig anledningen till att du litar på certifikatet. Tilliten kommer från att Root CA:n finns som en betrodd trust anchor i klientens trust store.
QUESTION 12
Kan du kryptografiskt verifiera att:
SERVER CERT was signed by INTERMEDIATE CA

utan att samtidigt behöva "tro" att CA:n är en bra organisation?

Ja. Du kan kryptografiskt kontrollera att signaturen stämmer. Det är en annan fråga än om du väljer att lita på utfärdaren som trust anchor. Kryptografisk verifiering och tillit är alltså inte exakt samma sak.
QUESTION 13
Du får ett certifikat och dess SHA-256 fingerprint från organisationens säkerhetsansvarige via telefon. Du jämför sedan fingerprint med certifikatet du fått över nätverket. Vad har du gjort?
Du har gjort en form av out-of-band-verifiering. Du använder en separat kanal för att verifiera att certifikatet du fått är det certifikat organisationen förväntar sig.
[ BOSS ] // CRYPTO FORENSICS
BOSS 01 // TWO BLOBS

En elev säger:

"Certifikatet borde väl innehålla: CERTIFICATE HASH SIGNED HASH annars kan datorn inte jämföra?"

Förklara varför klienten inte behöver få originalhashen skickad till sig.

Klienten har redan certifikatets innehåll. Den kan därför själv köra samma hashfunktion över det signerade innehållet. Det som behöver följa med är den digitala signaturen samt information om vilka algoritmer som används.
BOSS 02 // EVIL CERTIFICATE

Mallory kopierar ett legitimt certifikat för bank.example. Hon byter den publika nyckeln i certifikatet mot sin egen. All annan text behålls.

Varför fungerar inte detta?

Den publika nyckeln ingår i den data som CA:n har signerat. När Mallory ändrar nyckeln ändras det signerade innehållet. Den ursprungliga CA-signaturen verifierar därför inte längre. Mallory kan skapa en ny signatur med sin egen privata nyckel, men den signaturen är inte en giltig signatur från den CA som klienten förväntar sig.
BOSS 03 // SIGNED AND ENCRYPTED

Alice skickar Bob:

Encrypt_Bob( message, Signature_Alice(message) )

Bob lyckas dekryptera med sin privata nyckel. Betyder det automatiskt att meddelandet kom från Alice?

Nej. Att Bob kan dekryptera betyder i första hand att innehållet har krypterats så att hans nyckel kan användas för dekryptering. Bob måste fortfarande verifiera Alices digitala signatur med Alices publika nyckel. Kryptering och signering löser olika problem.
BOSS 04 // THE REAL TRUST PROBLEM

Bob har verifierat den digitala signaturen matematiskt. Men hur vet Bob att den publika nyckeln han använder verkligen är Alices?

Det är precis det problem som PKI och certifikat försöker lösa. Ett certifikat binder en identitet till en publik nyckel, och en betrodd CA signerar denna koppling. Men även PKI måste till slut börja i någon form av förhandstillit — en trust anchor.
[ TEACHER MODE ] // VARFÖR DE HÄR FRÅGORNA ÄR BRA

Frågor som "var ligger hashen?" eller "varför måste jag lita på root-certifikatet?" är ofta ett tecken på att studenten försöker bygga en faktisk mental modell istället för att memorera begrepp.

Ett bra sätt att svara är därför att hela tiden fråga:

1. Vilken DATA finns just nu? 2. Vilken OPERATION gör vi? 3. Vilken NYCKEL används? 4. Vilket NYTT VÄRDE produceras? 5. Vad skickas till mottagaren? 6. Vad kan mottagaren själv räkna fram?

Detta fungerar för hashfunktioner, digitala signaturer, certifikat och kryptering.

Det hjälper också till att undvika den vanliga sammanblandningen:

HASHING ≠ ENCRYPTION SIGNING ≠ ENCRYPTION CERTIFICATE ≠ PRIVATE KEY VALID SIGNATURE ≠ AUTOMATIC TRUST ENCRYPTED FOR BOB ≠ SIGNED BY ALICE
