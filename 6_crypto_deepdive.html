WHAT IS ACTUALLY SIGNED?

Digitala certifikat verkar enkla tills man börjar ställa de riktigt bra frågorna. Var finns hashvärdet? Är hash och digital signatur samma sak? Vad händer om någon ändrar certifikatet och räknar fram en ny hash? Vad är ett fingerprint? Och hur verifierar datorn egentligen att ett certifikat är äkta?

Målet är att följa datan genom hela processen och förstå vilka artefakter som skapas, vilka som sparas och vilka som kan beräknas på nytt.
00 // TRE ARTEFAKTER: DATA, HASH OCH SIGNATUR

När ett certifikat signeras finns tre viktiga saker att hålla isär:

D = DATA H = HASH(D) S = DIGITAL SIGNATURE

De är tre olika värden.

CERTIFICATE DATA │ ▼ HASH() │ ▼ H │ │ + PRIVATE KEY ▼ SIGNATURE ALGORITHM │ ▼ S

Hashvärdet H och den digitala signaturen S är alltså inte samma sak.

Hashvärdet är en mellanprodukt som används när signaturen skapas.

01 // VAD FINNS I ETT X.509-CERTIFIKAT?

Ett X.509-certifikat består förenklat av tre huvuddelar:

Certificate │ ├── tbsCertificate │ ├── signatureAlgorithm │ └── signatureValue

tbsCertificate betyder ungefär:

TO BE SIGNED CERTIFICATE

Det är den del som CA:n faktiskt signerade.

tbsCertificate │ ├── Serial Number ├── Issuer ├── Subject ├── Validity ├── Public Key ├── SAN ├── Extensions └── ...

När CA:n signerar detta sker ungefär:

tbsCertificate │ ▼ HASH │ ▼ H │ │ + CA PRIVATE KEY ▼ SIGNATURE │ ▼ S

Det färdiga certifikatet innehåller sedan:

┌──────────────────────────────┐ │ tbsCertificate │ ├──────────────────────────────┤ │ signatureAlgorithm │ ├──────────────────────────────┤ │ signatureValue = S │ └──────────────────────────────┘
HASHVÄRDET H BEHÖVER INTE LAGRAS SOM ETT SEPARAT FÄLT.

Klienten har redan tbsCertificate och kan därför beräkna hashvärdet själv när certifikatet ska verifieras.

[ BASIC ] // HASH ≠ SIGNATURE
QUESTION 01

CA:n beräknar SHA-256 över certifikatets tbsCertificate.

Vad produceras?

A) En digital signatur
B) Ett hashvärde
C) En publik nyckel
B. Hashfunktionen producerar ett hashvärde. Signaturen skapas först i nästa steg.
QUESTION 02

Vad behövs utöver hashvärdet för att skapa den digitala signaturen?

CA:ns privata nyckel och en signeringsalgoritm.
QUESTION 03

Är hashvärdet och den digitala signaturen samma artefakt?

Nej. Hashvärdet är ett resultat från hashfunktionen. Den digitala signaturen är ett nytt kryptografiskt värde som skapas genom signeringsprocessen.
[ INTERMEDIATE ] // WHAT ACTUALLY EXISTS?
QUESTION 04

Vilka av följande finns normalt som delar av det färdiga X.509-certifikatet?

A) tbsCertificate
B) Ett separat lagrat H1
C) signatureAlgorithm
D) signatureValue
A, C och D. Hashvärdet som användes under signeringen behöver normalt inte lagras som ett separat fält.
QUESTION 05

Varför behöver inte hashvärdet lagras?

Klienten har redan den data som ska verifieras. Den kan därför själv beräkna:
H = Hash(tbsCertificate)
QUESTION 06

En elev säger:

"Men om H1 inte sparas, vad jämför datorn H2 med?"
Klienten gör inte generellt en enkel jämförelse:
H1 == H2
I stället används:
nyberäknad hash + signatureValue + CA public key │ ▼ VERIFY() │ ▼ VALID / INVALID
Signaturverifieringen avgör om signaturen är giltig för just den aktuella datan.
02 // VAD HÄNDER OM CERTIFIKATET ÄNDRAS?

Antag att certifikatet ursprungligen innehåller:

D1 = Subject = www.example.com Public Key = ABC123 SAN = www.example.com

CA:n skapar:

D1 │ ▼ Hash │ ▼ H1 │ ▼ Sign with CA private key │ ▼ S1

Certifikatet innehåller:

D1 + S1

Mallory ändrar sedan:

Subject = evil.example

Nu har hon:

D2 + S1

Mallory kan utan problem själv beräkna:

Hash(D2) = H2

Men det finns inget gammalt H1-fält att byta ut.

Problemet är den gamla signaturen:

D2 │ ▼ H2 │ ├──────── S1 │ └──────── CA Public Key │ ▼ VERIFY │ ▼ INVALID
FÖR ATT GÖRA DET ÄNDRADE CERTIFIKATET GILTIGT BEHÖVS EN NY SIGNATUR S2, OCH FÖR ATT SKAPA DEN BEHÖVS CA:NS PRIVATA NYCKEL.
[ CHALLENGE ] // MODIFY THE CERTIFICATE
QUESTION 07

Mallory ändrar certifikatets SAN från:

www.example.com

till:

evil.example

Kan Mallory räkna ut en ny hash?

Ja. Hashfunktioner är publika och vem som helst kan beräkna hashvärdet.
QUESTION 08

Kan Mallory sedan "lägga in den nya hashen" och få certifikatet att bli giltigt igen?

Nej. Det finns inget separat H1-fält som används på det sättet. Mallory behöver i stället skapa en ny giltig digital signatur.
QUESTION 09

Vad saknar Mallory för att kunna skapa den nya signaturen?

CA:ns privata nyckel. Det är där den viktiga säkerhetsegenskapen finns.
03 // FINGERPRINT ÄR INTE SIGNATUR-HASHEN

När du öppnar ett certifikat i Windows kan du se:

Tumavtryck / Fingerprint: ab9d0263244dd0326eb67015705a667e79cfe998

Detta är en hash som används för att identifiera certifikatet.

HELA CERTIFIKATET │ ▼ HASH │ ▼ FINGERPRINT

Det är alltså inte samma sak som den digest som används internt i certifikatets digitala signatur.

Begrepp Vad är det?
Hash i signeringsprocessen Mellanprodukt som används när signaturen skapas
Digital signatur Kryptografiskt värde som ligger i certifikatet som signatureValue
Fingerprint Hash av certifikatet som används för identifiering
[ PRACTICAL ] // FIND THE SIGNATURE
TASK 10 // WINDOWS

Öppna ett certifikat i Windows och leta efter:

[ ] Subject
[ ] Issuer
[ ] Public Key
[ ] SAN
[ ] Signaturalgoritm
[ ] Signatur
[ ] Tumavtryck

Jämför sedan:

SIGNATUR vs TUMAVTRYCK

Är de samma värde?

Nej. Tumavtrycket är ett fingerprint. Signaturen är certifikatets digitala signatur, motsvarande signatureValue.
TASK 11 // OPENSSL

Exportera ett certifikat som PEM och kör:

openssl x509 -in cert.pem -text -noout

Hitta:

Issuer Subject Validity Public Key X509v3 extensions Signature Algorithm Signature Value

Längst ner bör du kunna se något ungefär som:

Signature Algorithm: sha256WithRSAEncryption Signature Value: 52:34:8f:... 19:a2:71:... ...

Den stora hexblobben är den digitala signaturen.

TASK 12 // FINGERPRINT

Visa certifikatets fingerprint:

openssl x509 \ -in cert.pem \ -noout \ -fingerprint \ -sha256

Fråga:

Är detta värde samma sak som Signature Value?
Nej. Fingerprint är en hash av certifikatet. Signature Value är certifikatets digitala signatur.
[ ADVANCED ] // VERIFY THE CERTIFICATE
QUESTION 13

Klienten har följande:

tbsCertificate signatureValue Issuer Public Key

Vad gör klienten?

Klienten beräknar digesten över certifikatets signerade data och använder digesten tillsammans med signaturen och issuer-CA:ns publika nyckel i signaturverifieringen.
QUESTION 14

Om signaturen verifieras korrekt, betyder det automatiskt att du litar på CA:n?

Nej. Du har visat att signaturen kryptografiskt stämmer. Det är en separat fråga om CA:n finns i din trust store och är en trust anchor som klienten accepterar.
QUESTION 15

Vad händer längst upp i certifikatkedjan?

SERVER │ ▼ INTERMEDIATE CA │ ▼ ROOT CA
Root-certifikatet fungerar som trust anchor. Det är normalt självsignerat, men tilliten kommer inte från självsigneringen. Tilliten kommer från att klienten redan valt att lita på den root-CA:n.
04 // SIGNERA OCH KRYPTERA

Alice vill skicka en fil till Bob med både:

autentisering + riktighet och konfidentialitet.

En vanlig pedagogisk modell är:

ALICE
FILE │ ├── HASH │ │ │ ▼ │ SIGN │ │ │ ▼ │ SIGNATURE │ ▼ FILE + SIGNATURE │ ▼ ENCRYPT FOR BOB │ ▼ CIPHERTEXT
BOB
CIPHERTEXT │ ▼ DECRYPT │ ▼ FILE + SIGNATURE │ ├── HASH FILE │ └── VERIFY SIGNATURE │ ▼ VALID?
DETTA ÄR EN PEDAGOGISK MODELL. RIKTIGA PROTOKOLL OCH FORMAT KAN ANVÄNDA ANDRA KONSTRUKTIONER.
[ CHALLENGE ] // SIGN + ENCRYPT
QUESTION 16

Alice signerar först filen och krypterar sedan:

Encrypt_Bob( FILE, Signature_Alice(FILE) )

Vilken nyckel används för signaturen?

Alices privata nyckel.
QUESTION 17

Vilken nyckel används för att kryptera till Bob?

Bobs publika nyckel.
QUESTION 18

Bob lyckas dekryptera med sin privata nyckel. Bevisar detta att filen kom från Alice?

Nej. Bob måste fortfarande verifiera Alices digitala signatur med Alices publika nyckel. Kryptering och signering löser olika problem.
[ BOSS ] // CERTIFICATE FORENSICS
BOSS 01 // THE MISSING HASH

En elev säger:

"För verifiering borde certifikatet innehålla: DATA H1 SIGNATURE "

Förklara varför H1 inte behöver följa med.

Verifieraren har redan DATA. Därför kan verifieraren själv beräkna:
Hash(DATA)
Signaturen och issuer-CA:ns publika nyckel används sedan för att kontrollera att signaturen är giltig för denna data.
BOSS 02 // REPLACE H1?

Mallory ändrar certifikatet och räknar:

Hash(D2) = H2

Kan hon ersätta H1 med H2?

Nej, eftersom H1 normalt inte finns som ett separat fält att ersätta. Problemet är att den gamla digitala signaturen hör ihop med det ursprungliga innehållet. Mallory behöver skapa en ny giltig signatur.
BOSS 03 // EVIL PUBLIC KEY

Mallory kopierar ett certifikat men byter ut den publika nyckeln mot sin egen.

Varför fungerar inte certifikatet längre?

Den publika nyckeln ligger i det signerade certifikatinnehållet. När nyckeln ändras ändras tbsCertificate. Den gamla CA-signaturen verifierar därför inte längre.
BOSS 04 // FINGERPRINT TRAP

Mallory ändrar certifikatet och räknar sedan fram ett nytt SHA-256 fingerprint.

Har hon gjort certifikatet giltigt?

Nej. Fingerprint identifierar certifikatet. Det är inte en ersättning för den digitala CA-signaturen.
BOSS 05 // TRUST

Du har matematiskt verifierat certifikatets signatur.

Vad återstår fortfarande att avgöra?

Om utfärdaren finns i en certifikatkedja som slutar i en Root CA som klienten faktiskt litar på. Kryptografisk verifiering och tillit är relaterade, men inte exakt samma sak.
[ TEACHER MODE ] // MENTAL MODELL

När elever börjar fråga:

"Var finns hashen?" "Vad jämförs med vad?" "Kan jag bara skapa en ny hash?" "Är fingerprint samma hash?" "Vad är egentligen signaturen?"

är det ofta bättre att sluta prata i abstrakta termer och i stället alltid följa samma sex frågor:

1. Vilken DATA har vi? 2. Vilken OPERATION görs? 3. Vilken NYCKEL används? 4. Vilket NYTT VÄRDE skapas? 5. Vilka värden SPARAS? 6. Vilka värden kan mottagaren RÄKNA FRAM SJÄLV?

Den här modellen löser många vanliga missförstånd.

HASH ≠ SIGNATURE HASH ≠ FINGERPRINT SIGNATURE ≠ ENCRYPTION FINGERPRINT ≠ TRUST VALID SIGNATURE ≠ AUTOMATIC TRUST CERTIFICATE ≠ PRIVATE KEY
