HOW DOES A DIGITAL SIGNATURE ACTUALLY WORK?

Vad händer egentligen när en CA signerar ett certifikat? Vad är skillnaden mellan ett hashvärde och en digital signatur? Varför blir signaturen annorlunda om innehållet ändras? Och hur kan klienten verifiera certifikatet när det inte finns något separat hashvärde lagrat i certifikatet?

MÅLET ÄR ATT FÖRSTÅ RELATIONEN MELLAN DATA, HASH, DIGITAL SIGNATUR OCH VERIFIERING.
00 // FYRA SAKER ATT HÅLLA ISÄR

Vi börjar med fyra olika saker:

DATA HASHVÄRDE DIGITAL SIGNATUR NYCKEL

De är inte samma sak.

Begrepp Vad betyder det?
Data Det innehåll som ska skyddas och signeras
Hashvärde Ett värde som räknas fram från datan
Digital signatur Ett kryptografiskt värde som skapas med hjälp av hashvärdet och den privata nyckeln
Nyckel Privat nyckel används vid signering, publik nyckel vid verifiering
01 // STEG 1 — DATA BLIR ETT HASHVÄRDE

Antag att en CA ska skapa ett certifikat för:

example.com

Certifikatet innehåller exempelvis:

Subject Issuer Giltighetstid Publik nyckel SAN = example.com ...

Vi kallar allt det signerade innehållet:

DATA 1

Det första som sker är att en hashfunktion används:

DATA 1 │ ▼ HASH() │ ▼ H1

H1 är hashvärdet.

HASHVÄRDET ÄR ETT RESULTAT AV CERTIFIKATETS INNEHÅLL.
[ BASIC ] // DATA → HASH
QUESTION 01

Vad händer om vi ändrar:

example.com

till:

example.se

Kommer hashvärdet normalt att vara samma?

Nej. Datan har förändrats. Därför förändras normalt också hashvärdet.
example.com │ ▼ H1 example.se │ ▼ H2 H1 ≠ H2
QUESTION 02

Är hashvärdet hemligt?

Nej. Vem som helst kan använda samma hashfunktion och räkna fram hashvärdet från datan.
02 // STEG 2 — HASHVÄRDET ANVÄNDS FÖR ATT SKAPA SIGNATUREN

CA:n har nu:

H1

CA:n använder sedan:

H1 + CA:S PRIVATA NYCKEL

i signeringsprocessen.

DATA 1 │ ▼ HASH │ ▼ H1 │ │ + CA PRIVATE KEY ▼ SIGN │ ▼ S1

S1 är den digitala signaturen.

HASHVÄRDET OCH DEN DIGITALA SIGNATUREN ÄR TVÅ OLIKA SAKER.

Ett enkelt sätt att tänka är:

DATA ↓ HASH ↓ HASHVÄRDE ↓ SIGNERING MED PRIVAT NYCKEL ↓ DIGITAL SIGNATUR
[ INTERMEDIATE ] // SAME KEY — DIFFERENT DATA

Nu skapar samma CA två certifikat.

CERTIFICATE A
example.com │ ▼ DATA 1 │ ▼ HASH │ ▼ H1 │ │ CA PRIVATE KEY ▼ SIGN │ ▼ S1
CERTIFICATE B

Samma CA skapar nu ett certifikat för:

example.se

CA:n använder exakt samma privata nyckel.

example.se │ ▼ DATA 2 │ ▼ HASH │ ▼ H2 │ │ SAME CA PRIVATE KEY ▼ SIGN │ ▼ S2
QUESTION 03

Blir S1 och S2 samma digitala signatur eftersom CA:n använder samma privata nyckel?

Nej. Innehållet är olika. Därför får vi olika hashvärden:
DATA 1 → H1 DATA 2 → H2
Och signeringen görs utifrån olika hashvärden:
H1 + CA PRIVATE KEY → S1 H2 + CA PRIVATE KEY → S2
Därför blir signaturerna olika.
03 // DEN PRIVATA NYCKELN ÄR INTE DET ENDA SOM PÅVERKAR SIGNATUREN
CERTIFICATE A example.com │ ▼ H1 │ │ CA PRIVATE KEY ▼ S1 CERTIFICATE B example.se │ ▼ H2 │ │ SAME CA PRIVATE KEY ▼ S2
SAMMA PRIVATA NYCKEL + OLIKA DATA GER OLIKA DIGITALA SIGNATURER.

Den digitala signaturen är alltså kopplad till både:

DET SIGNERADE INNEHÅLLET + DEN PRIVATA NYCKELN
04 // VAD FINNS SEDAN I CERTIFIKATET?

Det färdiga certifikatet innehåller förenklat:

CERTIFIKAT ├── Certifikatets innehåll │ ├── Information om signeringsalgoritm │ └── Digital signatur S1

Det viktiga är:

CERTIFIKATETS DATA FINNS DIGITALA SIGNATUREN FINNS MEN H1 BEHÖVER INTE FINNAS SOM ETT SEPARAT FÄLT
DET FINNS ALLTSÅ INTE NÖDVÄNDIGTVIS ETT FÄLT DÄR DET STÅR: H1 = ABC123...

Varför behövs inte det?

För att klienten själv kan räkna fram hashvärdet från certifikatets innehåll.

[ INTERMEDIATE ] // NOW VERIFY IT

Nu får en klient certifikatet.

Klienten har:

CERTIFIKATETS DATA DIGITAL SIGNATUR S1

Klienten kan också få fram CA:ns publika nyckel via certifikatkedjan.

STEP 01 // CALCULATE THE HASH AGAIN

Klienten tar certifikatets signerade innehåll:

DATA 1

och använder samma typ av hashfunktion:

DATA 1 │ ▼ HASH() │ ▼ H2

Vi kallar klientens nyberäknade hashvärde för H2.

QUESTION 04

Var finns H1 som klienten ska jämföra H2 med?

Det finns normalt inget separat lagrat H1-fält. Klienten gör alltså inte en vanlig jämförelse:
H1 == H2
mot två hashfält. I stället används H2 tillsammans med den digitala signaturen och CA:ns publika nyckel i signaturverifieringen.
05 // VAD HÄNDER I VERIFY?

Nu har klienten tre viktiga saker:

H2 DIGITAL SIGNATUR S1 CA:S PUBLIKA NYCKEL

Dessa används av signaturverifieringen:

CERTIFIKATETS DATA │ ▼ HASH │ ▼ H2 │ │ S1 ─────┼──────┐ │ │ CA │ │ PUBLIC ─┘ │ KEY │ ▼ VERIFY │ ┌──────┴──────┐ │ │ VALID INVALID

Det här är den centrala modellen.

VERIFY KONTROLLERAR OM DEN DIGITALA SIGNATUREN ÄR GILTIG FÖR DET HASHVÄRDE SOM KLIENTEN PRECIS HAR RÄKNAT FRAM.

CA:ns publika nyckel används för att göra denna kontroll.

Vi behöver alltså inte tänka:

"Var finns gamla H1?"

utan:

"Är S1 en giltig signatur för H2 med CA:ns publika nyckel?"
06 // VERIFY — ENKLASTE MENTALA MODELLEN

Tänk att funktionen får tre saker:

VERIFY( hashvärde, digital signatur, publik nyckel )

Och svarar:

VALID eller INVALID

Exempel:

H2 + S1 + CA PUBLIC KEY │ ▼ VERIFY │ ▼ VALID

Det betyder:

Den digitala signaturen S1 är giltig för det hashvärde H2 som klienten räknade fram.
EXAKT HUR VERIFY GÖR DEN MATEMATISKA KONTROLLEN BEROR PÅ SIGNATURALGORITMEN. I DEN HÄR UPPGIFTEN FOKUSERAR VI PÅ FÖRSTÅELSEN, INTE DEN UNDERLIGGANDE MATEMATIKEN.
[ CHALLENGE ] // MALLORY CHANGES THE CERTIFICATE

Originalcertifikatet:

example.com │ ▼ H1 │ │ CA PRIVATE KEY ▼ S1

Certifikatet skickas ut som:

DATA 1 + SIGNATURE S1
STEP 01 // MALLORY MODIFIES IT

Mallory ändrar:

example.com

till:

example.se

Nu är certifikatets data annorlunda.

DATA 2
QUESTION 05

Kan Mallory beräkna hashvärdet för DATA 2?

Ja. Mallory kan beräkna:
DATA 2 │ ▼ HASH │ ▼ H2
Hashning är inte hemlig.
QUESTION 06

Kan Mallory bara "byta H1 till H2"?

Nej. Det finns inget separat H1-fält som hon behöver eller kan ersätta på det sättet. Problemet är den digitala signaturen. Certifikatet har fortfarande:
S1
och S1 skapades för det ursprungliga innehållet.
STEP 02 // CLIENT VERIFIES THE MODIFIED CERTIFICATE

Klienten får nu:

DATA 2 + GAMLA SIGNATUREN S1

Klienten räknar:

DATA 2 │ ▼ HASH │ ▼ H2

Sedan:

H2 + S1 + CA PUBLIC KEY │ ▼ VERIFY │ ▼ INVALID
QUESTION 07

Vad skulle Mallory behöva för att det modifierade certifikatet ska bli giltigt?

Hon skulle behöva skapa en ny digital signatur:
DATA 2 │ ▼ HASH │ ▼ H2 │ │ CA PRIVATE KEY ▼ SIGN │ ▼ S2
Men Mallory har inte CA:ns privata nyckel.
07 // CA KAN SKAPA S2 — MALLORY KAN INTE

Den legitima CA:n kan göra:

example.com │ ▼ H1 │ │ CA PRIVATE KEY ▼ S1 example.se │ ▼ H2 │ │ SAME CA PRIVATE KEY ▼ S2

Mallory kan däremot bara komma så här långt:

example.se │ ▼ H2 │ ▼ ??? ↑ MISSING: CA PRIVATE KEY
SÄKERHETEN LIGGER INTE I ATT HASHVÄRDET ÄR HEMLIGT. SÄKERHETEN LIGGER I ATT MALLORY INTE KAN SKAPA EN NY GILTIG CA-SIGNATUR.
[ PRACTICAL ] // FIND IT IN A REAL CERTIFICATE
TASK 01 // OPEN THE CERTIFICATE

Öppna ett certifikat i Windows eller med OpenSSL.

Leta efter:

Subject Issuer Validity Public Key SAN Signature Algorithm Signature Fingerprint / Tumavtryck
TASK 02 // OPENSSL

Om certifikatet är sparat som:

cert.pem

kör:

$ openssl x509 -in cert.pem -text -noout

Leta efter:

Signature Algorithm Signature Value

Den stora mängden hexdata under Signature Value är certifikatets digitala signatur.

QUESTION 08

Kan du hitta ett vanligt separat fält som innehåller:

H1 = hashvärdet som CA:n använde
Nej. Hashvärdet behöver inte ligga där som ett separat fält. Verifieraren kan beräkna hashvärdet igen från certifikatets data.
08 // FINGERPRINT ÄR INTE SAMMA SAK

När du öppnar ett certifikat kan du också se:

Fingerprint eller Tumavtryck

Det är en annan användning av en hashfunktion.

HELA CERTIFIKATET │ ▼ HASH │ ▼ FINGERPRINT

Det används bland annat för att identifiera ett specifikt certifikat.

Begrepp Vad är det?
Hashvärde vid signering Beräknas från signerad data och används i signeringsprocessen
Digital signatur Skapas med hjälp av hashvärdet och den privata nyckeln
Fingerprint Hash som används för att identifiera certifikatet
FINGERPRINT ≠ DIGITAL SIGNATUR
[ CHALLENGE+ ] // UNDERSTAND VERIFY
QUESTION 09

Klienten har:

CERTIFICATE DATA SIGNATURE S1 CA PUBLIC KEY

Vad gör klienten först?

Klienten räknar fram ett hashvärde från certifikatets signerade data.
DATA ↓ HASH ↓ H
QUESTION 10

Vad används hashvärdet till efter det?

Det används tillsammans med:
DIGITAL SIGNATUR + CA:S PUBLIKA NYCKEL
i signaturverifieringen.
QUESTION 11

Vad frågar VERIFY egentligen?

Förenklat:
"Är den här digitala signaturen giltig för det här hashvärdet med den här publika nyckeln?"
Om ja:
VALID
Om nej:
INVALID
09 // MEN VEM ÄGER DEN PUBLIKA NYCKELN?

Vi har nu förstått den kryptografiska verifieringen.

HASH + SIGNATURE + CA PUBLIC KEY │ ▼ VERIFY

Men ytterligare en fråga återstår:

VARFÖR LITAR VI PÅ DENNA CA?

Det är här certifikatkedjan kommer in:

SERVER CERTIFICATE │ ▼ INTERMEDIATE CA │ ▼ ROOT CA

Root CA:n finns normalt redan som betrodd i operativsystemets eller webbläsarens trust store.

SIGNATURVERIFIERING KONTROLLERAR KRYPTOGRAFIN. TRUST STORE AVGÖR VILKA ROOT CA:S KLIENTEN VÄLJER ATT LITA PÅ.

[ BOSS ] // EXPLAIN THE WHOLE THING
BOSS 01 // HASH VS SIGNATURE

Är hashvärdet och den digitala signaturen samma sak?

Nej.
DATA ↓ HASH ↓ HASHVÄRDE ↓ SIGNERING ↓ DIGITAL SIGNATUR
Hashvärdet används i processen för att skapa signaturen.
BOSS 02 // SAME PRIVATE KEY

Samma CA använder samma privata nyckel för att signera:

example.com och example.se

Varför blir signaturerna olika?

Innehållet är olika. Därför får vi:
DATA 1 ≠ DATA 2 ↓ H1 ≠ H2 ↓ S1 ≠ S2
BOSS 03 // WHERE IS H1?

Klienten räknar fram H2. Var finns gamla H1?

H1 behöver inte finnas som ett separat lagrat hashfält. Klienten använder H2 tillsammans med signaturen och CA:ns publika nyckel i VERIFY.
BOSS 04 // VERIFY

Vad används vid signaturverifiering?

Förenklat:
NYBERÄKNAT HASHVÄRDE + DIGITAL SIGNATUR + CA PUBLIC KEY ↓ VERIFY
BOSS 05 // MALLORY

Mallory ändrar certifikatet. Vad kan hon göra?

Mallory kan:
✓ Ändra data ✓ Räkna fram en ny hash ✓ Räkna fram ett nytt fingerprint
Men Mallory kan inte:
✗ Skapa en ny giltig CA-signatur utan CA:S PRIVATA NYCKEL
BOSS 06 // ONE SENTENCE

Förklara en digital signatur med en enda mening.

En digital signatur är ett kryptografiskt värde som skapas från den signerade datan, vanligtvis via ett hashvärde, med hjälp av den privata nyckeln och som senare kan verifieras med den publika nyckeln.
[ TEACHER MODE ] // MENTAL MODEL

Målet är att eleverna ska kunna rita två flöden från minnet.

SIGNERING

DATA ↓ HASH ↓ HASHVÄRDE ↓ SIGN + PRIVATE KEY ↓ DIGITAL SIGNATUR

VERIFIERING

DATA ↓ HASH ↓ HASHVÄRDE ─────────┐ │ SIGNATURE ─────────┤ │ PUBLIC KEY ────────┘ │ ▼ VERIFY │ VALID / INVALID

Eleven bör förstå följande:

1. Hash och signatur är olika saker. 2. Signaturen skapas utifrån den signerade datan. 3. Ändras datan ändras hashvärdet. 4. Ändrad data kräver en ny signatur. 5. Samma privata nyckel kan skapa många olika signaturer eftersom datan som signeras är olika. 6. Hashvärdet är inte hemligt. 7. Ett nytt hashvärde räcker inte för en angripare. 8. En ny giltig signatur kräver den privata nyckeln. 9. Klienten räknar själv fram hashvärdet igen. 10. Hashvärdet används tillsammans med signaturen och den publika nyckeln i VERIFY.

Undvik att gå in på:

ASN.1 DER DigestInfo RSA padding modulär exponentiering ECDSA r/s signaturkodning

om målet för lektionen är förståelse snarare än implementation.

Om elever frågar exakt vad som händer inne i VERIFY kan man svara:

"Signaturalgoritmen använder hashvärdet, signaturen och den publika nyckeln för att matematiskt kontrollera om signaturen är giltig för just detta innehåll."

Det räcker på denna nivå.
