HOW DOES THE CLIENT ACTUALLY VERIFY IT?

Vi vet att en CA har signerat ett certifikat. Men hur kan klienten kontrollera signaturen när det inte finns något separat hashvärde lagrat i certifikatet?

I den här labben följer vi exakt vilka data som finns, vilket hashvärde klienten räknar fram och hur detta används tillsammans med den digitala signaturen.

MÅLET ÄR INTE ATT MEMORERA "HASH + PRIVATE KEY = SIGNATURE". MÅLET ÄR ATT FÖRSTÅ VAD VERIFIERAREN FAKTISKT GÖR.
00 // VAD FINNS I CERTIFIKATET?

Ett X.509-certifikat kan förenklat beskrivas som:

Certificate │ ├── tbsCertificate │ ├── signatureAlgorithm │ └── signatureValue

tbsCertificate betyder ungefär:

TO BE SIGNED CERTIFICATE

Den innehåller bland annat:

tbsCertificate │ ├── Version ├── Serial Number ├── Issuer ├── Validity ├── Subject ├── Subject Public Key ├── SAN ├── Extensions └── ...

Den digitala signaturen ligger separat som:

signatureValue
DET FINNS NORMALT INTE ETT SEPARAT FÄLT SOM HETER H1 DÄR DEN URSPRUNGLIGA HASHEN LIGGER.
01 // NÄR CA:N SKAPAR SIGNATUREN

Antag att certifikatets signerade data kallas D.

D = DER-kodad tbsCertificate

CA:n beräknar:

D │ ▼ HASH │ ▼ H1

Exempel:

H1 = SHA256(D)

Sedan använder CA:n sitt privata nyckelmaterial och den valda signeringsalgoritmen.

H1 │ │ + CA PRIVATE KEY │ ▼ SIGNATURE ALGORITHM │ ▼ S1

Det färdiga certifikatet innehåller därför ungefär:

┌─────────────────────────────┐ │ D = tbsCertificate │ ├─────────────────────────────┤ │ signatureAlgorithm │ ├─────────────────────────────┤ │ S1 = signatureValue │ └─────────────────────────────┘

H1 var en mellanprodukt.

[ BASIC ] // WHERE DID H1 GO?
QUESTION 01

Vilka två centrala saker har klienten tillgång till direkt från certifikatet?

tbsCertificate och signatureValue. Den har alltså både datan som signerades och signaturen.
QUESTION 02

Behöver klienten få H1 skickat till sig?

Nej. Klienten har tbsCertificate och kan själv köra samma hashfunktion över exakt samma data.
QUESTION 03

Vad får klienten om den beräknar:

SHA256(tbsCertificate)
Ett nytt beräknat hashvärde. Vi kallar detta:
H2
Om certifikatets signerade data är exakt oförändrad kommer H2 att motsvara den digest som användes när signaturen skapades.
02 // NU KOMMER SJÄLVA VERIFIERINGEN

Klienten har nu:

D = tbsCertificate H2 = Hash(D) S1 = signatureValue Q = CA public key

Det viktiga är att klienten INTE gör:

H1 == H2

eftersom det inte finns något separat H1 att läsa från certifikatet.

I stället gör klienten konceptuellt:

VERIFY( CA_PUBLIC_KEY, SIGNATURE_VALUE, H2 )

Verifieringsalgoritmen svarar:

VALID eller INVALID
DET ÄR SIGNATUREN SOM ÄR DET KRYPTOGRAFISKA REFERENSVÄRDET. HASHEN RÄKNAS FRAM PÅ NYTT AV VERIFIERAREN.
03 // MÅSTE MAN "BACKA" SIGNATUREN?

Det beror på signeringsalgoritmen.

Det är därför farligt att generellt säga:

"Klienten dekrypterar signaturen med CA:s publika nyckel."

Det fungerar som en förenklad pedagogisk bild för vissa äldre RSA-signaturer, men det beskriver inte digitala signaturer generellt.

Algoritm Vad händer vid verifiering?
RSA PKCS#1 v1.5 En publik RSA-operation görs på signaturen och en signerad kodningsstruktur kontrolleras. Där ingår information om digesten.
RSA-PSS En annan RSA-signaturkodning används. Det är inte bara att "plocka ut en hash".
ECDSA Signaturen består av matematiska värden r och s. Ingen gammal hash "dekrypteras" ur signaturen.
DEN GENERELLA MODELLEN ÄR DÄRFÖR: VERIFY(PUBLIC_KEY, SIGNATURE, DATA/DIGEST)
[ INTERMEDIATE ] // RSA PKCS#1 v1.5

Nu använder vi RSA PKCS#1 v1.5 eftersom den är pedagogiskt bra för att förstå var jämförelsen faktiskt sker.

STEP 01 // CLIENT HASHES THE CERTIFICATE
tbsCertificate │ ▼ SHA-256 │ ▼ H2

H2 är klientens egen beräkning.

STEP 02 // CLIENT PROCESSES THE SIGNATURE

Klienten har:

S1 = signatureValue CA public key = n e

För RSA kan den publika RSA-operationen förenklat beskrivas:

M = S1^e mod n

Resultatet är inte vanlig klartext.

Det är en strukturerad RSA-signaturkodning.

STEP 03 // VERIFY THE ENCODING

För PKCS#1 v1.5 innehåller den verifierade strukturen konceptuellt:

PKCS#1 SIGNATURE ENCODING 00 01 FF FF FF FF ... │ └── padding DigestInfo │ ├── Hash algorithm = SHA-256 │ └── Digest = H1

Här finns alltså den digestinformation som skapades under signeringen kodad inne i RSA-signaturstrukturen.

STEP 04 // THE COMPARISON

Nu har verifieraren två värden:

Från egen beräkning: H2 = SHA256(tbsCertificate) Från RSA-signaturverifieringen: H1 = digest representerad i den signerade strukturen

Då kan verifieraren kontrollera:

H1 == H2 ?
Om de matchar och RSA-signaturkodningen i övrigt är giltig:
SIGNATURE VALID
Om de inte matchar:
SIGNATURE INVALID
04 // HELA RSA-FLÖDET
CA SKAPAR tbsCertificate │ ▼ SHA-256 │ ▼ H1 │ │ + CA PRIVATE KEY ▼ RSA PKCS#1 SIGN │ ▼ S1 CERTIFICATE: ┌────────────────────────────┐ │ tbsCertificate │ ├────────────────────────────┤ │ sha256WithRSAEncryption │ ├────────────────────────────┤ │ signatureValue = S1 │ └────────────────────────────┘ KLIENT VERIFIERAR tbsCertificate │ ▼ SHA-256 │ ▼ H2 S1 │ │ CA public key ▼ RSA VERIFY │ ▼ digest information │ ▼ H1 H1 == H2 ? │ │ YES NO │ │ ▼ ▼ VALID INVALID
[ CHALLENGE ] // MALLORY CHANGES THE CERTIFICATE
SCENARIO

Originalet:

D1 │ ▼ SHA256 │ ▼ H1 │ ▼ SIGN │ ▼ S1

Mallory ändrar:

SAN = www.example.com till SAN = evil.example

Nu har hon D2.

QUESTION 04

Kan Mallory beräkna:

H2 = SHA256(D2)
Ja. Hashfunktionen är publik. Det finns inget hemligt med H2.
QUESTION 05

Certifikatet innehåller fortfarande gamla:

S1

Vad händer när klienten verifierar?

Klienten räknar:
Hash(D2) = H2
Den gamla signaturen S1 hör däremot till det ursprungliga D1/H1. Verifieringen misslyckas.
QUESTION 06

Kan Mallory bara stoppa in H2 någonstans?

Nej. Det finns inget separat H1-fält som hon kan ersätta. Hon behöver skapa en helt ny giltig:
S2
och det kräver CA:ns privata nyckel.
[ ADVANCED ] // VARFÖR "DECRYPT THE SIGNATURE" ÄR FEL GENERELLT
ECDSA

Antag att certifikatet i stället använder ECDSA.

Signaturen består då ungefär av:

signature = (r, s)

Klienten beräknar fortfarande:

H2 = Hash(tbsCertificate)

Men den "öppnar" inte signaturen och hittar H1.

I stället används H2, r, s och CA:ns publika nyckel i elliptisk-kurv-matematik.

H2 + (r,s) + CA public key │ ▼ ECDSA VERIFY │ ▼ VALID / INVALID
DETTA ÄR VARFÖR DEN SÄKRA GENERELLA FORMULERINGEN ÄR: SIGNATURE VERIFICATION — INTE "DECRYPT SIGNATURE".
[ PRACTICAL ] // INSPECT A REAL CERTIFICATE
TASK 01 // VIEW CERTIFICATE
$ openssl x509 -in leaf.pem -text -noout

Leta efter:

Issuer Subject Subject Public Key Info X509v3 Subject Alternative Name Signature Algorithm Signature Value
TASK 02 // IDENTIFY SIGNATURE ALGORITHM

Du kan till exempel se:

Signature Algorithm: sha256WithRSAEncryption

Det berättar bland annat vilken hashfunktion som ingår i signaturmekanismen.

TASK 03 // VERIFY THE CERTIFICATE CHAIN

Om du har:

leaf.pem intermediate.pem root.pem

kan du låta OpenSSL verifiera kedjan:

$ openssl verify \ -CAfile root.pem \ -untrusted intermediate.pem \ leaf.pem

Vid lyckad verifiering:

leaf.pem: OK

OpenSSL gör då bland annat den kryptografiska signaturverifieringen åt dig.

[ PRACTICAL++ ] // CALCULATE THE DIGEST YOURSELF

I den här övningen gör vi flödet mer synligt.

Installera Python-paketet:

$ pip install cryptography
STEP 01 // LOAD CERTIFICATES
from cryptography import x509 with open("leaf.pem", "rb") as f: leaf = x509.load_pem_x509_certificate(f.read()) with open("issuer.pem", "rb") as f: issuer = x509.load_pem_x509_certificate(f.read())
STEP 02 // GET THE EXACT SIGNED BYTES
tbs = leaf.tbs_certificate_bytes print("TBS length:", len(tbs))

Det här är viktigt:

HASHEN SKA BERÄKNAS ÖVER DEN EXAKTA DER-KODADE tbsCertificate-DATAN — INTE ÖVER TEXTEN SOM OPENSSL VISAR.
STEP 03 // GET SIGNATURE
signature = leaf.signature print("Signature length:", len(signature)) print(signature.hex())

Detta är certifikatets:

signatureValue
STEP 04 // FIND HASH ALGORITHM
hash_algorithm = leaf.signature_hash_algorithm print(hash_algorithm.name)

Exempel:

sha256
STEP 05 // CALCULATE H2 YOURSELF
from cryptography.hazmat.primitives import hashes hasher = hashes.Hash(hash_algorithm) hasher.update(tbs) H2 = hasher.finalize() print("H2:", H2.hex())

Nu har DU gjort samma typ av digestberäkning som behövs vid signaturverifieringen.

H2 = Hash(tbsCertificate)
STEP 06 // GET ISSUER PUBLIC KEY
public_key = issuer.public_key() print(public_key)

Det är utfärdarens publika nyckel som ska verifiera certifikatets signatur.

[ PRACTICAL+++ ] // VERIFY YOUR H2 DIRECTLY

Om certifikatet använder RSA PKCS#1 v1.5 kan vi uttryckligen låta biblioteket verifiera den hash vi själva räknat fram.

from cryptography.hazmat.primitives.asymmetric import padding from cryptography.hazmat.primitives.asymmetric import utils public_key.verify( signature, H2, padding.PKCS1v15(), utils.Prehashed(hash_algorithm) ) print("SIGNATURE VALID")

Här händer exakt det vi försöker förstå:

DU RÄKNADE: H2 = Hash(tbsCertificate) SEDAN GER DU VERIFY(): H2 signatureValue CA public key RESULTAT: VALID / EXCEPTION
DET FINNS FORTFARANDE INGET SEPARAT H1-FÄLT I CERTIFIKATET. SIGNATURVERIFIERINGSALGORITMEN KONTROLLERAR ATT SIGNATUREN ÄR GILTIG FÖR DEN DIGEST DU HAR BERÄKNAT.
[ CHALLENGE ] // BREAK ONE BYTE
TASK

Kopiera den signerade datan:

modified = bytearray(tbs)

Ändra en byte:

modified[20] ^= 0x01

Beräkna en ny digest:

hasher = hashes.Hash(hash_algorithm) hasher.update(bytes(modified)) H3 = hasher.finalize() print("Original H2:", H2.hex()) print("Modified H3:", H3.hex())

Försök sedan verifiera samma gamla signatur mot H3:

public_key.verify( signature, H3, padding.PKCS1v15(), utils.Prehashed(hash_algorithm) )
Verifieringen ska misslyckas. Du har nu själv demonstrerat:
D1 → H2 → S1 verifies D2 → H3 → S1 does NOT verify
Det är inte hashen i sig som angriparen inte kan skapa. Angriparen kan skapa H3. Det är en ny giltig signatur för H3 som angriparen saknar CA:ns privata nyckel för att skapa.
05 // FINGERPRINT — EN HELT ANNAN HASH

Visa certifikatets fingerprint:

$ openssl x509 \ -in leaf.pem \ -noout \ -fingerprint \ -sha256

Detta kan ge:

SHA256 Fingerprint= A1:B2:C3:D4:...

Detta är inte H2 ovan.

Värde Beräknas över Syfte
H2 tbsCertificate Signaturverifiering
signatureValue Skapas från signerad data/digest + privat nyckel Bevis för signaturen
Fingerprint Vanligen hela certifikatet Identifiera certifikatet
[ BOSS ] // EXPLAIN IT WITHOUT MAGIC
BOSS 01

En elev säger:

"Klienten räknar H2. Men var finns H1 som den ska jämföra mot?"
Det finns normalt inget separat H1-fält. Klienten använder sin nyberäknade digest tillsammans med signatureValue och CA:ns publika nyckel i signaturverifieringen. För RSA PKCS#1 v1.5 kan verifieringen pedagogiskt ses som att digestinformationen som signaturen representerar kontrolleras mot den digest klienten själv räknat fram.
BOSS 02

Varför kan Mallory inte bara räkna fram H3 efter att hon ändrat certifikatet?

Hon kan. Problemet är inte H3. Problemet är att hon inte kan skapa en giltig digital signatur för H3 med CA:ns privata nyckel.
BOSS 03

Varför bör man inte säga:

"Man dekrypterar signaturen med den publika nyckeln."
Det är en RSA-specifik förenkling och beskriver inte digital signaturverifiering generellt. ECDSA fungerar exempelvis inte så alls. Den generella termen är:
VERIFY SIGNATURE
BOSS 04

Fyll i:

DATA ↓ ______ ↓ DIGEST ↓ ______ ↓ SIGNATURE
DATA ↓ HASH FUNCTION ↓ DIGEST ↓ SIGNATURE ALGORITHM + PRIVATE KEY ↓ SIGNATURE
BOSS 05

Fyll i verifieringssidan:

tbsCertificate ↓ ______ ↓ H2 H2 + ______ + ______ ↓ VERIFY ↓ VALID / INVALID
tbsCertificate ↓ HASH ↓ H2 H2 + signatureValue + CA public key ↓ VERIFY ↓ VALID / INVALID
[ TEACHER MODE ] // THE FIVE QUESTIONS

För varje signaturövning, låt eleverna svara på fem frågor:

1. VILKEN DATA SIGNERADES? 2. VILKEN HASHFUNKTION ANVÄNDES? 3. VILKEN SIGNATUR HAR VI? 4. VILKEN PUBLIK NYCKEL SKA VERIFIERA DEN? 5. VAD RÄKNAR VERIFIERAREN FRAM SJÄLV?

Den viktiga formuleringen är:

Verifieraren beräknar själv digesten över den signerade datan. Digesten används sedan tillsammans med signaturen och signerarens publika nyckel för att verifiera signaturen.

Undvik helst:

"Hashen ligger i certifikatet." "Klienten jämför två hashfält." "Signaturen är hashen." "Alla signaturer dekrypteras med den publika nyckeln."
