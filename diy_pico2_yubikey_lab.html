// BEFORE YOU START
CHALLENGE 01

What are you actually building?

You need:

  • Raspberry Pi Pico 2 (RP2350)
  • a USB data cable
  • a Windows, Linux or macOS computer
  • a modern browser

You do not need a separate Raspberry Pi, Arduino, breadboard or custom PCB.

A normal USB flash drive stores data. A FIDO2 authenticator is an active device: it receives protocol messages and performs cryptographic operations. 
USB storage:
private-key.pem  →  computer reads secret

FIDO2 authenticator:
challenge  →  authenticator  →  cryptographic response
                    │
               secret stays here

Question: Why is the second model interesting from a security perspective?

Reveal discussion

A readable private-key file can potentially be copied by software that can access it. A hardware authenticator instead exposes operations: the computer asks it to perform an authentication operation and receives the result. The private credential material does not need to be exported during normal authentication.

// FLASH THE AUTHENTICATOR
CHALLENGE 02

From development board to FIDO2 device

We will use the open-source Pico FIDO2 firmware.

github.com/LibreFido/pico-fido2

  1. Read the current project/release instructions.
  2. Download firmware intended for Raspberry Pi Pico 2 / RP2350.
  3. Disconnect the Pico 2.
  4. Hold BOOTSEL while connecting the USB cable.
  5. Release BOOTSEL.
  6. Verify that the Pico boot volume appears. On Pico 2 it is normally RP2350.
  7. Copy the appropriate .uf2 firmware to the device.
  8. Allow the board to reboot.

Open-source firmware changes over time. Do not blindly use an old filename from a lab sheet; identify the current RP2350/Pico 2 release yourself.

Question: The device appeared as USB storage during flashing. Why can it appear as something completely different after reboot?

Reveal discussion

USB devices describe themselves to the host. The firmware running on the microcontroller determines which USB interfaces and protocols the device exposes. The BOOTSEL ROM provides one behaviour; the newly installed authenticator firmware provides another.

CHALLENGE 03

Prove that something changed

Inspect the Pico after flashing.

On Linux, start with:

lsusb

On Windows, investigate Device Manager or PowerShell.

Try to identify:

  • Vendor ID (VID)
  • Product ID (PID)
  • USB interfaces/classes exposed by the device

Question: What evidence shows that you are no longer merely talking to a USB mass-storage device?

Reveal discussion

Look at how the operating system enumerates the device and which interfaces it exposes. A FIDO authenticator normally communicates using the FIDO HID transport rather than behaving like ordinary removable storage.

// WEBAUTHN
CHALLENGE 04

Create a credential

Use a reputable WebAuthn/FIDO2 test environment, or a test mechanism recommended by the firmware project.

Register your Pico 2 as an authenticator.

Do not just celebrate when it works. Pay attention to what the browser asks you to do and what information appears to be associated with the new credential.

Then disconnect the Pico, attempt authentication, reconnect it, and authenticate again.

Question: What does the server need in order to verify a later authentication? Does it need your private key?

Reveal discussion

WebAuthn uses public-key credentials. The authenticator retains the secret/private credential material required to produce an assertion, while the relying party keeps information that allows the assertion to be verified. The server does not need the authenticator's private key.

CHALLENGE 05

Follow the challenge

Explain the authentication path in your own words:

WEB APPLICATION
       │
    WebAuthn
       │
 BROWSER / OS
       │
     CTAP2
       │
    USB HID
       │
    PICO 2

Then complete this simplified sequence:

server creates __________
          ↓
authenticator performs __________
          ↓
server performs __________
Reveal discussion

A simplified answer is: the server creates a fresh challenge, the authenticator creates the required cryptographic assertion using its credential, and the relying party verifies the returned assertion. The real WebAuthn data structures contain more than just a bare challenge and signature, which is worth investigating if you continue deeper.

// RELYING PARTIES
CHALLENGE 06

One key. Two sites.

If possible, register the same Pico 2 with two different WebAuthn test relying parties.

Investigate:

  • Does FIDO2 simply reuse one universal credential everywhere?
  • What is a Relying Party ID?
  • How does this design affect credential reuse?
  • Why is the RP relationship relevant to phishing resistance?
Reveal discussion

FIDO/WebAuthn credentials are scoped to relying parties rather than being a universal shared password sent to every site. The authenticator/browser protocol also binds authentication to the relying-party context. This is an important reason WebAuthn credentials behave differently from reusable passwords.

// USER PRESENCE
CHALLENGE 07

Connected does not mean approved

Assume malware is running on the computer while your security key is connected. The computer can communicate with the authenticator.

Investigate the FIDO concepts:

  • UP — User Presence
  • UV — User Verification

Question: Why might an authenticator require a physical interaction or local verification before completing an operation?

Reveal discussion

User Presence establishes that a user is physically interacting with the authenticator for the operation. User Verification goes further by verifying the user locally, for example using a PIN or another supported mechanism. Merely having the device connected should not necessarily authorize every possible operation.

// THREAT MODEL
CHALLENGE 08

What does your key actually protect?

Consider three attackers:

ATTACKER A
Malware running on your computer.

ATTACKER B
Has stolen the Pico and has physical access to it.

ATTACKER C
Controls a phishing site impersonating a legitimate service.

For each attacker, explain:

  • what FIDO2 helps protect against,
  • what depends on the authenticator hardware/firmware,
  • what attacks may still remain possible.
Reveal discussion

Do not treat “uses FIDO2” as equivalent to “secure against everything.” Protocol design, client compromise, physical extraction, authenticator implementation and user verification address different parts of the threat model. A useful security analysis states which attacker capabilities a control is intended to resist.

CHALLENGE 09

USB file vs hardware authenticator

Compare these three authentication mechanisms:

A: password

B: USB drive containing private.pem

C: FIDO2 credential on Pico 2

For each one, reason about:

  • Can the authentication secret be copied?
  • Does secret material need to be exposed to the host during normal use?
  • What changes if the host contains malware?
  • What changes if the physical device is stolen?
  • How does phishing affect the mechanism?
Reveal discussion

The important distinction is not simply “hardware versus software.” Ask where the secret exists, whether it is exportable, what operation the host is allowed to request, how the credential is bound to a relying party, and what an attacker gains from compromising the host or stealing the device.

// GO DEEPER
CHALLENGE 10 // OPTIONAL+

Read the implementation

Open the Pico FIDO2 source code.

Find code related to at least three of these:

  • credential creation
  • assertions
  • CTAP
  • PIN / user verification
  • user presence
  • cryptographic key material

You do not need to understand every line.

Goal: move from:

"I copied a UF2 file."

to:

"I can roughly explain what this firmware is doing."
Reveal discussion

Security engineers frequently rely on libraries and existing implementations. Understanding the architecture, trust boundaries and important security-sensitive components is often more valuable than pretending every component was written from scratch.

CHALLENGE 11 // EXTREME MODE

Build it yourself

Build the firmware from source rather than using the pre-built UF2.

Document:

  1. toolchain,
  2. SDK/dependencies,
  3. build commands/options,
  4. generated UF2,
  5. flash procedure.

Then investigate:

What are USB VID and PID, and why should a product developer care who owns the identifiers being used?

Reveal discussion

VID/PID values identify USB devices and products to the host. Building a prototype and shipping a product are different situations; identifiers, firmware provenance, update security and production provisioning all become part of the engineering problem.

// FINAL CHECK
CHALLENGE 12

Show that you understand it

To complete the bonus lab, demonstrate to the teacher:

  • a Raspberry Pi Pico 2 running FIDO2 authenticator firmware,
  • successful WebAuthn registration,
  • successful authentication,
  • an explanation of challenge → authenticator → assertion → verification,
  • why this is different from storing private.pem on a USB drive.

One final question:

Have you built a YubiKey?

Reveal discussion

Not literally. YubiKey is a Yubico product. You have built a FIDO2/WebAuthn-compatible hardware authenticator. Protocol compatibility does not automatically give a development board the physical protection, production controls, provisioning, certifications or other security properties of a commercial security key.
